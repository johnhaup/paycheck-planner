# HAU-334: release gate failed @ 2f74b82, "Cannot run sharded tests with sequential execution" (2026-11-14)

## Cause
Not an app regression and not a stale flow: no flow ran. The runner's v2 gate (`linear-runner/v2/internal/jobs/gate.go`)
now erases four `Paycheck Planner Release Gate` simulators and runs
`maestro --udid a,b,c,d test .maestro/qa/ --shard-split 4`. Maestro 2.11 refuses a sharded run when the workspace
`config.yaml` has an `executionOrder`, and ours had one since HAU-299 (to run `deep-link-approval` first).

## Change (flows only, no app code)
- Deleted `.maestro/qa/config.yaml` (it held nothing but the `executionOrder`) and `.maestro/qa/deep-link-approval.yaml`.
- New `.maestro/qa/subflows/approve-deep-link.yaml`: launch with `clearState`, `openLink: paycheck-planner://income`,
  wait up to 60 s for `Open|No income yet`, optional tap on "Open", then require "No income yet". Maestro runs only
  the top-level files of the folder, so it is not a flow of its own.
- Every flow with an `openLink` step (17 of 23) runs it from `onFlowStart`. With shards any flow can be the first on
  a freshly erased simulator, so the approval cannot live in one flow that runs first. The gate's retry of a failed
  flow alone is covered the same way.
- `docs/AGENT_CONTEXT.md`: the Maestro line described `config.yaml` and `deep-link-approval`; no longer true.

## Verified
- `maestro check-syntax` on all 23 flows, `bunx tsc --noEmit`, `bun run lint`.
- The gate's own steps by hand: erased and booted the four `Paycheck Planner Release Gate` simulators, installed
  the gate's Release build of 2f74b82 (copied from DerivedData to `/tmp/hau334/`), ran the command above:
  23/23 in 10m 53s (shards 6/6, 6/6, 6/6, 5/5) at load 100-750. `commands.json` shows the Open tap COMPLETED in
  exactly one flow per shard (pro-mock-store, paywall, settings-text-size, chart-amounts), the first with a link.
- Android not run (no emulator here); the subflow has no iOS-only step and Income's empty state is the same text.

## Pitfalls
- A new flow that uses `openLink` needs the `onFlowStart` hook, or it fails when it is first on a fresh simulator.
- Never add `executionOrder` to a workspace config here: it breaks every sharded gate before a flow starts.
- Do not wait a fixed time for the alert. The first version kept HAU-299's optional 10 s wait for "Open"; at load
  500+ the alert came up later, over the flow's own launch, and the first run failed 5 flows that way. Waiting on
  "alert or Income tab" has no guess in it and costs an approved simulator only the extra launch.
- zsh does not word-split `$U`; use an array for the simulator UDIDs.

## Follow-up (linear-runner, not this repo)
- The gate could approve the scheme itself after the erase (see the HAU-299 note); then the hook could go.
