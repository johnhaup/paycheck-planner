# HAU-905: Paychecks no longer crashes on a tab return with no income

## What changed and why
- `homeIndex` in `app/(tabs)/(paychecks)/index.tsx` was `rows.length - 1` when no paycheck is on or after
  today, so with no rows it was -1. The HAU-903-era tab-return effect calls `goHome(false)` → `jumpTo(homeIndex)`,
  and `attemptJump` only special-cases index 0, so it called `scrollToIndex({ index: -1 })`: VirtualizedList's
  invariant throws (Render Error on dev, app closes on Release).
- `homeIndex` is now clamped to ≥ 0 (`Math.max(rows.length - 1, 0)`). An empty list's jump goes to 0, the
  offset path, like the mount effect already did for `!hasIncome`. Every other user of `homeIndex`
  (`rows[homeIndex]`, `initialNumToRender`, `hidden.set(homeIndex > 0)`, short-ahead check) is unchanged
  for non-empty rows and harmless at 0 for empty ones.

## Verified (Runner 1, dev build on Metro)
- Scratch flow (sample data → Income → swipe-left + tap trash on Mesa Health at y 411, then Brightline Co. at
  y 339 → Paychecks → assert Welcome, "Add income source", no "Render Error"): passes. With the clamp reverted
  the same flow shows the `scrollToIndex out of range: requested index -1` Render Error.
- Welcome checked in dark and light.
- With income: scrolled to December, Income tab, back to Paychecks → lands on the home paycheck (Nov 27).
  Today's sample dates put home at index 0; the index > 0 path is untouched by the clamp.
- `bunx tsc --noEmit`, `bun run lint` clean. No unit test setup. Core suite not run (gate runs it).

## Pitfall
- A swipe on an Income row only reveals the trash; the delete needs a tap on it (x 345 in points).
