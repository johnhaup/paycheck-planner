# HAU-299: release gate failed 13 of 15 flows @ 547542c (2026-11-12)

## Cause
Not an app regression and not a stale flow. The ticket's screenshot shows SpringBoard's "Open in Paycheck Planner?"
alert over the welcome screen. iOS raises it the first time a simulator opens the `paycheck-planner://` scheme, it
survives relaunches and `clearState`, and Maestro never taps it. `linear-runner/gate.sh` now erases the gate
simulator before every run (commit `ed8062d`, disk reclaim), so every gate starts unapproved: `settings` and
`paychecks` (no `openLink`) pass, `pro-mock-store` fails on its first deep link, the rest time out at launch.
Same signature as the fresh-install runs in the brain's `qa.md`.

## Change (flows only, no app code)
- `.maestro/qa/deep-link-approval.yaml`: launch, `openLink: paycheck-planner://`, wait up to 10 s for "Open"
  (optional), tap it (optional), then require the welcome screen and no "Open" button. Untagged, so Android runs it
  too (no alert there; it passes after the 10 s wait).
- `.maestro/qa/config.yaml`: `executionOrder.flowsOrder: [deep-link-approval]` runs it before the other flows,
  `continueOnFailure: true` so the suite still runs if it fails.
- `docs/AGENT_CONTEXT.md`: the Maestro line said nine flows and mock store in `pro.yaml`; both were stale.

## Verified
- `maestro check-syntax` on the new flow, `bunx tsc --noEmit`, `bun run lint`.
- NOT run on a simulator (engineer runs have none). QA: `xcrun simctl erase` a simulator (or use one that never
  ran the app), install the Release build, run the whole suite; `deep-link-approval` must be the first flow in the
  log and the result 16/16. An already-approved simulator does not exercise the fix.

## Pitfalls
- Do not tag the flow `ios`: the Android gate runs with `--exclude-tags ios`, and a `flowsOrder` entry that is
  filtered out may make Maestro refuse to start (not tested).
- The gate re-runs a failed flow alone (`maestro test .maestro/qa/<flow>.yaml`); the approval from the suite run is
  still on the simulator then, so the retry does not need the config.

## Follow-up (linear-runner, not this repo)
- `gate.sh` could approve the scheme itself after the erase, for every app: `xcrun simctl spawn <udid> defaults
  write com.apple.launchservices.schemeapproval "com.apple.CoreSimulator.CoreSimulatorBridge-->paycheck-planner"
  -string com.johnhaup.paycheckplanner` (not tested here). Plate Weight's gate has the same exposure if its flows use
  `openLink`.
