# HAU-699: money counts move from their first frame

## What changed and why
- `useCountUp` no longer runs a Reanimated timing that sends each frame to JS with `scheduleOnRN` → `setState`. A JS frame loop
  shared by all counts (`requestAnimationFrame`) starts on the frame after the commit and updates every count in one render
  per frame. The step is capped at two 60 Hz frames, so a late frame slows the count down instead of skipping most of it.
  If the screen is not focused (`useIsFocused`), the count snaps to the new value. Reduce Motion still fades, unchanged.
- This alone did not remove the hold. Timing logs (`console.log(performance.now())`, read from the Metro log) showed why: every
  store change on the pay date screen re-rendered the whole Paychecks screen behind it twice. The second pass was the header
  floor reset (`setHeaderFloor` from `onLayout`). Together that was about 500 ms of JS work in the dev build before the first
  count frame. A count drawn by React cannot move while the JS thread is busy.
- New `src/hooks/useFocusedStore.ts`: `useStore(selector)` that keeps the value it had when the screen was last focused. The
  Paychecks screen's four store reads and `usePaycheckCardRenderer`'s `assignments` use it. A tap on the pay date screen now
  re-renders only that screen: render → effect → first count frame took about 90 ms (it was about 530 ms).
- `freezeOnBlur` would have done this, but Expo Router's native stack forces it off ("has no effect in Expo Router").

## Verified (Runner 1, dev build on Metro)
- Sample data → Brightline Nov 27 → + on Rent, recorded and read at 20 fps.
  - Before (from the issue): 3 frames at $883.00, then -$539.85 in one frame (86% of the distance).
  - With only the frame loop: still 4 frames at $883.00, then $658.33, $52.83 …
  - After: "Short by $767.00" appears in the same frame as $382.99, then -$87.85, -$408.93, -$608.41, -$715.31,
    -$758.55, -$766.96, -$767.00. The largest step is the first one, about 30% of the distance.
- Back on Paychecks: the old values stay up for about 600 ms (the pop finishes, then focus arrives, then one full list
  render), then the hero counts $1,270.15 → -$379.85 and Rent joins the card. Accepted: every change still shows, and it
  costs nothing while a count is running.
- Reduce Motion: fade with no count. Light and dark mode. `maestro test .maestro/qa/`: 6/6 passed. tsc and lint clean.
- Not run: a Release build (the runner does not allow local builds); the release gate runs the suite in Release.

## Follow-ups / pitfalls
- Fold job: brain `decisions.md` 2026-11-21 Motion rules (4), "the timing runs on the UI thread and hands React each frame's
  value", should now read "a shared JS frame loop starting the frame after the commit, capped steps, snaps off-screen; screens
  behind another hold their store data (`useFocusedStore`)".
- Lesson: before tuning an animation that lags, time the JS thread. Here the cost was a hidden screen re-rendering.
- During a swipe back, Paychecks shows the values from before the pay date screen until the gesture ends.
