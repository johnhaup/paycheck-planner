# HAU-877: pro and expenses flows wait for the keyboard

## What changed and why
- The first keyboard on a freshly reset simulator is slow. `pro.yaml` tapped Save while the
  number pad was still rising, so the tap landed on its `0` key (field read 21000, the sheet stayed open).
  `expenses.yaml` swiped before the keyboard was up, which then covered "Update expense".
- Only `.maestro/qa/` changed, no app code:
  - `pro.yaml`: after `inputText: "2100"`, wait for the number pad's `Delete` key, then
    `waitForAnimationToEnd` (the sheet finishes moving up), `assertVisible: "2100"`, then Save.
  - `expenses.yaml` due-day block: the same wait (the `Delete` key on iOS only, since Android's keyboard keys
    are not in the hierarchy; `waitForAnimationToEnd` on both) after `inputText: "18"` and after
    `tapOn: "18"`. After the section-label tap that drops the pad there is also a `waitForAnimationToEnd`, so both
    "Update expense" taps come after the keyboard has settled.
- On iOS the number pad's keys are hierarchy elements (`1`…`0`, `.`, `Delete`, `Dictate`). In
  these two forms `Delete` matches only the key, so `visible: "Delete"` means the keyboard is up.

## Verified (Runner 1, iPhone 17 Pro, iOS 27.0, dev build on Metro)
- `maestro test .maestro/qa/` 6/6 twice in a row (9m 27s, 9m 30s). The pro screenshot shows a
  $2,100.00 paycheck with $1,003.00 left over. The expenses run reaches "Due the 18th".
- Not verified: the first run was not on a freshly reset simulator, because an earlier partial run on this
  simulator had already brought up the keyboard. Release build not run (agents may not build). The steps
  use nothing that only exists in a dev build.

## Pitfalls
- Do not wait on the keyboard's `Delete` key on a screen that has its own "Delete" text (expense
  edit form scrolled down, swipe actions). Anchor it (`rightOf: "0"`) if a flow needs that.
