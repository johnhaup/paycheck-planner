# HAU-571: expo-dev-client, so runner agents use the shared dev build

## What changed
- `expo-dev-client ~58.0.21` added with `bunx expo install` (package.json, bun.lock). No app code,
  no config plugin entry, no `eas.json` change (`production-local` already says
  `developmentClient: false`).
- Every `launchApp` in `.maestro/qa/` (13, in all 6 flows) now carries `"--initialUrl": ${METRO_URL}`,
  `"-EXDevMenuShowsAtLaunch": "NO"`, `"-EXDevMenuShowFloatingActionButton": "NO"` and
  `"-EXDevMenuIsOnboardingFinished": "YES"`, ahead of the flow's own arguments. The bare
  `- launchApp` in `smoke.yaml` became a block. `ship/screenshots.yaml` is untouched (Release only).
- CLAUDE.md, "Shipping and QA": one paragraph on the dev build and `METRO_URL`.

## Verified (Runner 1, iOS 27.0, load 300-700)
- `runner devapp` in the worktree built the dev client (fingerprint `21a95ca7…`, now in
  `work/paycheck-planner/_dev/`), installed it and opened it on Metro :8082. No launcher or dev
  menu on screen after a Maestro launch.
- Dev build, `maestro test -e METRO_URL=http://127.0.0.1:8082 .maestro/qa/`: 5/6 on the first run.
  `settings` failed once (the tap on "Español" did nothing; it was the first flow, during the first
  bundle at load 700) and passed 2/2 alone straight after. `pro` (mock store arguments next to the
  dev ones) passed.
- Release simulator build (`expo run:ios --device generic --configuration Release --output`):
  no `EXDevLauncher.bundle` / `EXDevMenu.bundle` (the Debug app has both), no `EXDevLauncher`
  symbol in the binary; only the `EXDevMenuInterface` protocol names, from the interface pod that
  Expo links in every configuration. It has `main.jsbundle` and launches straight into the app.
- Release build, suite with **no** `METRO_URL` set (Maestro passes the literal `${METRO_URL}`,
  the app ignores it): 6/6 in 7m 26s.
- `bunx tsc --noEmit` and `bun run lint` clean.

## Not verified
- `bun run ship:ios` itself was not run: `eas build --local` with `autoIncrement` and the remote
  version source takes a build number from Expo's servers, and the runner owns that. The Release
  check above uses the same Podfile and configuration; `expo-dev-launcher` and `expo-dev-menu`
  are `debugOnly` in their `expo-module.config.json`, so an archive cannot link them.
- Android (Linux worker): the dev client's Android side and the gate there were not built.

## Pitfalls
- `bunx expo-local-ship ios --help` is not a help screen: it starts a ship (it stopped at the
  missing `credentials.json` here). Read `~/Projects/expo-local-ship/src/index.ts` instead.
