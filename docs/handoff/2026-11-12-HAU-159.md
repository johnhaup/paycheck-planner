# HAU-159: amount sheets keep Save above the number pad (2026-11-12)

## What changed
- New `src/components/AmountSheet.tsx`, the shared body of `app/paycheck-amount.tsx` and
  `app/expense-amount.tsx` (they were copies of each other; both had the bug).
- Cause: the sheets are `fitToContents` form sheets. At the largest text sizes the content is
  taller than the space between the sheet's top and the number pad; UIKit cannot lift the sheet
  any higher, so the bottom of the content, Save included, sat under the keys.
- Fix: the body has `maxHeight = window height - keyboard height - top inset - 16`
  (`useKeyboardState` from react-native-keyboard-controller). Save and "Use usual amount" are
  pinned at the bottom of that space; title, date, input and hint are in a `ScrollView` above
  them. When the text does not fit, it starts scrolled so the input is at the top of the visible
  part. `keyboardShouldPersistTaps="handled"` so Save takes the first tap.
- Standard text sizes: the cap does not bind, layout is unchanged.

## Verified
- `bunx tsc --noEmit` and `bun run lint` clean. Not run on a simulator (engineer runs have none).

## For QA
- Pro, largest accessibility size, Paychecks → open a paycheck → tap the pay amount: Save fully
  visible above the number pad, the amount field visible, tapping Save saves (no stray digit).
  Scroll the text up/down inside the sheet: title and hint reachable.
- Same on a bill amount (pay date detail → tap a bill's amount). Save a custom amount, reopen:
  both Save and the "use default" button are above the keys.
- Default text size: both sheets look as before, no scrolling, sheet hugs its content.
- Swipe the keyboard away (if it goes): the sheet should not leave a blank band or clip Save.

## Pitfalls / unknowns
- A `fitToContents` sheet's content wrapper is `position: absolute` with no bottom, so its
  height comes only from its children: `flex: 1` does nothing there, bound it with `maxHeight`.
- Not known without a device: whether react-native-screens re-measures the sheet when the body
  shrinks as the keyboard appears. Either way the body is at the sheet's top and ends above the keys.
- Android: untested; if the window already resizes for the keyboard the cap is merely lower.
