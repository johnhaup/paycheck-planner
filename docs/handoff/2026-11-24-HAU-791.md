# HAU-791: edits to existing rows were lost on relaunch

**Cause.** Since HAU-787, every synced table has cloud-sync's `_sync_<table>_upd` trigger, which does `INSERT OR REPLACE INTO _sync_changes`. An outer `INSERT … ON CONFLICT DO UPDATE` (upsert) imposes its own conflict policy (ABORT) on the statements inside the trigger. So when the row was already queued in `_sync_changes` (always without iCloud, and after any edit that has not synced yet), the trigger failed with `UNIQUE constraint failed: _sync_changes…`. The whole save rolled back and `guarded()` swallowed the error. Plain `UPDATE`, plain `INSERT` and `ON CONFLICT DO NOTHING` do not hit it (checked in bun:sqlite).

**What changed.**
- `src/db/budget.ts` `saveBudgetChanges`: an edited entity is now `UPDATE … WHERE id = ?` (it still clears the tombstone and keeps `created_at`), with a plain `INSERT` only when no row changed. `upsertSql` became `insertSql(spec, ignoreExisting)`; the legacy import uses `insertSql(spec, true)` (DO NOTHING, unchanged behaviour).
- `src/db/settings.ts` `writeSetting`: the same UPDATE-then-INSERT. It had the same bug: a second currency or hideCents change before a sync was lost.
- Fixed in the app, not in `@johnhaup/expo-cloud-sync`, because that repo is outside this worktree. The trigger itself is still fragile (see follow-ups).

**Verified.**
- New `sync.test.ts` case: two rounds of edits to every entity kind before any sync, plus two currency writes. Both persist and stay queued. It fails on the old code with the exact UNIQUE error. `bun test` 37/37 pass, tsc and lint are clean.
- Runner 1, dev build: the ticket's steps (sample data, Internet 70 → 9000, terminate, relaunch) keep $9,000.00, and the SQLite file has 9000. Marking Internet paid survives a relaunch.
- `expenses.yaml` now has an edit-and-relaunch step (Internet 70 → 90, Brightline total $1,477.33 → $1,497.33; the XXXL block's total was updated to match). The full flow passes with the fix and fails at the post-relaunch total without it.

**Follow-ups / pitfalls.**
- Module: write `_sync_changes` in the triggers with `INSERT … ON CONFLICT DO NOTHING` instead of `INSERT OR REPLACE`. Any future app code that upserts into a synced table would break the same way. Until then: never use `ON CONFLICT … DO UPDATE` on a synced table.
- `guarded()` turns a failed write into a `console.warn`, which is how this went unnoticed. Consider a toast or a dev-only throw.
