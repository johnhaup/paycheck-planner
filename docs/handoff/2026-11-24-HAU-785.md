# HAU-785: Android formats dates and amounts in the picked language (2026-11-24)

## What changed and why
- Cause: `toLocaleTag()` built `<language>-<device region>` (`de-US`, `ar-US`, `he-US`) and kept it when
  `new Intl.DateTimeFormat(tag)` did not throw. Hermes on Android never throws for a pair it has no data for;
  it formats in the device default (en-US). Spanish worked because `es-US` exists.
- New `src/utils/localeTag.ts` (`pickLocaleTag`, pure): keeps `<language>-<region>` only when
  `resolvedOptions().locale` has the requested language, else the bare language (`no` also accepts ICU's `nb`).
  Tags with a region or script (`pt-BR`, `zh-Hans`) are unchanged. Memoised per language and region.
- Bare `ar` gave Arabic-Indic digits (١٬٢٧٠٫١٥) on Android while iOS (ar-US) shows Latin ones, so a fallback
  to bare Arabic is `ar-u-nu-latn`; Hermes keeps the `nu` extension.
- `toLocaleTag()` in `src/stores/localeStore.ts` calls it. Money, dates, the date picker and the currency
  sheet all read that one tag, so no formatter changed.
- Tests: `src/utils/localeTag.test.ts` (Android-like, iOS-like, throwing and aliasing resolvers).

## Follow-ups and pitfalls
- Picking an RTL language reloads the app and closes Settings: a Maestro `back` after it leaves the app.
- On Android an unknown language-region tag does not throw: check `resolvedOptions().locale`. Do not switch to
  `supportedLocalesOf` or `localeMatcher: "lookup"`; lookup uses a different locale list on Android.
